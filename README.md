# StudySheet · 学习记录

记录每天「大科目 → 事项」的学习时长，暂停时选原因，结束后自动扣除暂停时间，
之后按周分析、帮助提升学习效率。

## 使用场景

共用一台设备（家里平板 / 一台手机），多人轮流记录。**不需要账号登录**，
点一下人名即切换身份；人名只是分组标签，不是权限边界 —— 任何拿到这台设备的人
都能看到全部记录。

数据全部存在本机浏览器 IndexedDB 里，不上传服务器。

## 技术栈

| 层 | 选型 | 原因 |
| --- | --- | --- |
| 构建 | Vite + React 19 + TypeScript | 手机浏览器直接访问，改动即时生效 |
| 样式 | Tailwind v4 | 移动端表单密集， utility 写起来快 |
| 存储 | Dexie（IndexedDB） | 本地优先、离线可用，不需要后端即可跑通 |
| 状态 | zustand | 计时器状态跨组件共享 |
| 时间 | dayjs | 起止时间与格式化 |
| 图表 | ECharts（按需引入） | 曲线 / 堆叠柱 / 饼 / 条形一套搞定 |
| 测试 | Vitest | 统计口径必须可回归 |

「图表」页懒加载，ECharts 那 599 KB 不进首屏包，每天必开的记录页仍是 372 KB。

数据层集中在 `src/db/repo.ts`：UI 不直接调 Dexie。将来要支持**各自手机、数据汇总**
（多端同步）时，只把这一层换成后端 API（建议 Next.js + Prisma + PostgreSQL，或直接用
Supabase 省掉鉴权和部署），其余代码不动。唯一的例外是备份导入 `src/lib/merge.ts` ——
它要一次事务操作六张表，属于同一层，换后端时一起换。

## 核心数据模型

```
Profile       人名，共用设备上的分组标签
Subject       大科目（语文…）
TaskType      事项（默写 / 预习…），subjectId 为 null 表示通用事项
PauseReason   暂停原因，自定义项也存进字典并按使用次数排序
StudySession  一次记录，结束时冻结 netMs / gapsMs / breaksCount
SessionSegment work / break 事件流
```

`SessionSegment` 存成事件流而不是一个 `pauseMs` 字段，是为了周报能回答
「走神平均发生在开始后第几分钟」「哪类事项暂停最多」。净时长 = Σ work 段。

## 两个实现约束

**计时不靠 setInterval 累加。** 只存时间戳，每次渲染用 `Date.now()` 反算，
所以切后台、锁屏再回来都不会丢时间。见 `src/hooks/useNow.ts`。

**日期按本地时区取。** `toISOString()` 是 UTC，UTC+8 的用户在 10-19 00:30 学习会
被错标成 10-18。见 `src/lib/time.ts` 的 `dayKey`。

## 统计口径（M2）

`src/lib/stats.ts` 是唯一口径，图表和周报都读它。三条容易算错的规则：

**净时长按自然日归属。** 23:40→00:20 这条记录，「今天」视图只算 20 分钟，
「昨天」只算 15 分钟，不是整段算给开始那天。

**补录也进图表。** 补录没有 work/break 事件流，整段 `startAt→endAt` 视为一段
学习；否则图表里看不到它，而今日列表又有，两处数字对不上。

**环比用「上期同期」。** 本周只过了 1 天时，拿它比上周完整 7 天必然显示暴跌，
所以把上期也截成同样的天数，标签写作「环比同期」。

## 周报（M3）

`src/lib/report.ts` 把指标翻译成结论，**纯确定性规则，不接大模型**：这是纯本地
应用，没有服务端也没有 API Key；更关键的是每条结论都必须能被追溯到具体数字，
否则用户没法判断它是不是在胡说。所以 `Finding` 带 `evidence: string[]`，UI 原样显示。

三类规则值得单独记：

**样本不足要自己说。** 少于 3 条记录或少于 3 天有记录时标 `reliable: false`，
UI 挂「样本偏少」。需要样本量的结论各自有门槛：漏记要 `reliable`，时段规律要
≥3 条计时记录，星期分布要 ≥3 个不同的周几有记录 —— 补录没有事件流，
所以它再多也不会触发时段结论。

**星期对比必须先归一。** `weekdayMinutes` 是跨周求和的量，本月有 5 个周六、
4 个周三时，直接比总量比的是「这个月有几天」而不是「哪天更能学」。所以按
`weekdayCounts` 折成平均每个周几，且只数窗口内已过去的天。

**好消息和坏消息不互斥。** 「连续记录 3 天」和「一个月只记了 3 天」得同时说；
写成 `else if` 就只剩下好听的那条。

**不足 1 分钟不等于没记录。** 时长存的是毫秒、显示四舍五入到分钟，一条 24 秒的
记录 `totalMinutes` 是 0。这时说「这个时段还没有记录」是假话，改成「不到 1 分钟」；
也不能据此报「环比减少 100%」—— 那是四舍五入造出来的，所以趋势要求本期和上期
都 ≥30 分钟。

建议最多 3 条 —— 再多不会执行。人员对比模式下不出报告，几个人的数据混在一起
说「你偏科」是错的。

## 导出与备份（M4）

数据只在一台设备的浏览器里，不清出去就等于没有。两种格式用途不同，
`src/lib/export.ts` 一个负责给人看，一个负责给程序读回。

**CSV 给 Excel，必须带 UTF-8 BOM。** 没有 BOM 时 Excel 按 GBK 猜编码，中文全成乱码。
分钟保留 1 位小数 —— 写成整数会把一条 24 秒的记录显示成 0，而「暂停明细」列用同一套
舍入，否则会出现「暂停(分) 0.1、明细里 (0分)」这种自己和自己对不上。跨零点的记录
**不拆开**：导出的是原始事实，按天摊开是图表的口径，混在一张表里就没法核对了。

**JSON 备份存原始事件流**，不存 `now`，时长由段还原；因此它不带 BOM（加了会让 `jq`
和标准 `JSON.parse` 报错）。同时记下导出时的 UTC 偏移 —— 时长不受时区影响，但
「这条算周几」受，跨时区恢复时界面上会提示。

导入有三条不能省的规矩（`src/lib/merge.ts`）：

**未结束的计时在导入时按导出的那一刻收尾。** 否则换到另一台设备，`boot()` 会把它
捡起来从 `startAt` 一路数到现在 —— 三天前导出的备份能凭空变出 70 小时学习时长。

**字典按名字合并，不按 id。** 新设备一打开就自动铺了一套默认科目，备份里也有同名
的一套，按 id 认会变成两个「语文」，图表把同一门课悄悄拆成两半。事项按「科目+名字」
去重，避免不同科目下的「默写」被错并。代价是两台设备上真不同的「物理」会被并成
一条 —— 这能靠改名补救，而重复科目不会提示你。

**段的主键必须重新分配。** `segments` 是自增 id，本机的 12 号段和备份里的 12 号段
是两条不同的东西；导入时剥掉 id 交给 Dexie，段与记录的关联靠 `sessionId`，不受影响。

替换导入是「先清六张表再写」放在同一个事务里，写入失败整体回滚，不会留下
「库清空了但没写进去」的空档。这个选择不可撤销，所以确认界面把两种模式的后果
并排写出来，而不是弹一个 `confirm()`。

## 轻量跨设备（M6-lite）

没有后端时，「同步」能做的其实只有一件事：把备份从 A 设备交到 B 设备，
外加别让人忘了备份。`src/lib/share.ts` 管搬运，`src/lib/sync.ts` 管「该不该催」。

**发送按体验排序走三条路：系统分享 → 剪贴板 → 存成文件。** iOS / Android 上
`navigator.share` 能直接把文件送进微信、隔空投送、文件 App，用户不用去下载目录
里认文件名，所以它排第一。用户按「取消」也表现为异常，那种情况要**真的**落一个
文件下来 —— 备份还没交出去，只回一句「改用下载」是空话。剪贴板有 200 KB 上限，
超了就走文件，并且说明的原因是「备份太大」而不是「这台浏览器不支持」：后者换个
浏览器就能好，用户该知道真相。非安全上下文（`http://` 局域网 IP）下剪贴板会被拒，
同样退回文件。

**接收端多一个「粘贴导入」。** 手抄、微信转发最常见的坏法是掉尾巴，所以括号
数对不上时报「内容不完整，很可能掉了尾巴，请重新完整复制一次」，而不是含糊的
「不是合法 JSON」。同时容忍代码块围栏、聊天软件加的引号和首尾空白。

**备份状态只回答「现在该不该再导一次」**，判据是上次导出的时间和当时的记录数
（记在 localStorage，不进备份本身 —— 它是关于备份的事实，跟着备份走会自我证明）。
新记录超过 3 天才升级成红色；CSV **不**算备份事件，它导不回。导入也算一次备份
事件：数据刚从别处进来，说明这台设备已经不是唯一副本，继续催「你从没备份过」是假话。

**记录页只拦一种情况**：有记录却从来没导出过。那是唯一会让数据全丢、而用户至今
没做任何防护的路径。「又记了几条」天天看只会被无视，留在设置页里。「不再提示」
顶 3 天而不是永久静音 —— 说的是数据可能全丢，静音它不该是一次点击的决定。

**要守的性质是：两台设备来回各导一次会并齐，且记录不会翻倍**（id 去重、字典按名字
合并），见 `src/lib/twodevices.test.ts` —— 它用真实的导出 → 序列化 → 解析 → 导入链路，
不是手搓的 fixture。真·多端同步（M6）时这几条都不作废：通道换成后端，判断「谁的设备」
换成邀请码，搬运之外才需要冲突合并。

## 阶段

- [x] **M1** 人员切换、科目/事项字典、计时器（开始 / 暂停选原因 / 继续 / 结束备注）、
      补录、今日列表
- [x] **M2** 今天 / 本周 / 本月 / 全部四个窗口；全部 / 单人 / 人员对比三种范围；
      每日堆叠柱、按科目曲线、按事项曲线、科目占比、暂停原因条形、
      暂停时机分布、最长专注、计划达成率、环比同期
- [x] **M3** 周报：趋势、连续与漏记、暂停密度与时机、时段与星期分布、偏科、
      计划达成、补录可信度，每条结论附证据数字 + 最多 3 条改进建议
- [x] **M4** 导出 CSV（带 BOM，Excel 直接可读）/ JSON 全量备份，导入支持合并与整库替换，
      未结束的计时自动收尾，字典按名字合并
- [x] **M6-lite** 轻量跨设备：系统分享 / 剪贴板 / 文件三条搬运通道，粘贴导入与截断识别，
      备份新鲜度提示，两台设备来回各导一次即并齐
- [ ] **M5** 拍照 OCR：识别作业清单生成待办，OCR 结果一律先进「草稿 + 确认」再入库
- [ ] **M6** 多端同步：引入后端与邀请码替代裸人名，搬运通道换成服务端，
      在此基础上才需要冲突合并（M6-lite 的备份格式与合并规则直接复用）

## 本地运行

```bash
npm install
npm run dev      # http://localhost:5173
npm test         # 统计口径回归（固定 Asia/Shanghai 时区）
npm run build
```
